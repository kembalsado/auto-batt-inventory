# Reports Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a shop-wide Reports page showing two cost-side totals — Purchases and Stock-out value — for a selected day, month, or year, with a per-day or per-month breakdown table.

**Architecture:** A new `lib/reports.ts` module does two bulk range queries (purchases via the session client + `batches_for_viewer`; stock-out value via the admin client + `movement_allocations`, the only client that can read it) and three composition functions (daily/monthly/annual) built on top. A new `/reports` page resolves the viewer's role and `canSeeCost` first and only calls the cost queries when that passes; otherwise it renders a short gated message and queries nothing. A new migration grants `service_role` the one table-level SELECT it's never had, since nothing has read `movement_allocations` until now.

**Tech Stack:** Next.js App Router (Server Components), Supabase (Postgres + PostgREST), Vitest.

**Spec:** `docs/superpowers/specs/2026-11-17-reports-design.md`

## Global Constraints

- Dates are Asia/Manila calendar dates ("YYYY-MM-DD" strings), via `manilaToday()` (`lib/date.ts`) — never a UTC `Date`.
- Purchases counts only `batches_for_viewer.source = 'purchase'` — opening-stock imports (`source = 'opening_stock'`) are excluded (confirmed with the owner).
- Both totals exclude voided movements (`stock_movements.voided_at is null`), checked through the movement, never inferred from `batches`/`movement_allocations` alone.
- Cost queries never run for a viewer `canSeeCost(role, settings)` says can't see cost — not "run and hide," actually skipped.
- `getStockOutValueByDate`'s `adminSupabase` parameter must be `createAdminClient()` (`lib/supabase/admin.ts`) — `movement_allocations` has no session-readable path at all (migration 0011).
- `getPurchasesByDate`'s `supabase` parameter must be the normal session client (`createServerClient()`) — never the admin client, because `batches_for_viewer`'s cost gate falls through to the global toggle only when there's no real `auth.uid()` (i.e. it would show the wrong thing for an owner viewing with the toggle off).
- No currency symbol in rendered amounts — match the existing Items/Stock List convention (plain `formatCurrency`, labeled columns, no "₱" prefix in the UI; the SQL audit-log summaries are the only place that symbol appears).

## Review Focus

- A period with zero movements of one type but some of the other (e.g. purchases but no sales that day) — each total must be independently correct, not both forced to zero or to each other's value. Covered by Task 2's mixed-activity test.
- A voided IN or voided OUT inside the queried range — must contribute nothing to either total, including the OUT case where its `movement_allocations` rows still physically exist. Covered by Task 2's void tests.
- An opening-stock import inside the queried range — must not inflate Purchases. Covered by Task 2's opening-stock test.
- A month/year with zero activity at all (new shop, or a future/past period nothing happened in) — totals and breakdown rows must come back as real zeros, not throw or return `undefined`. Covered by Task 3's empty-range test.
- A year view spanning the Dec 31/Jan 1 boundary and a leap-year February — date arithmetic is this app's known recurring bug class (see `lib/date.ts`'s own docstring). Covered by Task 3's year-rollup and leap-year tests.

- [ ] **Step 3: Implement `getPurchasesByDate` and `getStockOutValueByDate` in `lib/reports.ts`**

`getPurchasesByDate`: query `stock_movements` (`type = "IN"`, `voided_at is null`, `movement_date` between `startDate`/`endDate`) selecting `movement_date, quantity, batch_id`; collect distinct `batch_id`s; if none, return `new Map()`. Else query `batches_for_viewer` with `.in("id", batchIds)` selecting `id, unit_cost, source`; build an `id -> {unit_cost, source}` lookup; for each movement row where the matching batch's `source === "purchase"` and `unit_cost != null`, add `quantity * unit_cost` into a `Map<string, number>` keyed by `movement_date`.

`getStockOutValueByDate`: query `stock_movements` (`type = "OUT"`, `voided_at is null`, `movement_date` between `startDate`/`endDate`) selecting `id, movement_date` via `adminSupabase`; if none, return `new Map()`. Else query `movement_allocations` via `adminSupabase` with `.in("movement_id", ids)` selecting `movement_id, qty_allocated, unit_cost_at_allocation`; build an `id -> movement_date` lookup from the first query; for each allocation row, add `qty_allocated * unit_cost_at_allocation` into a `Map<string, number>` keyed by the matching movement's `movement_date`.

Both: throw on any Supabase `error`, same convention as `lib/calendar.ts`'s `getMonthActivity`.

- Produces:
  - `export interface AmountTotals { purchases: number; stockOutValue: number }`
  - `export interface DailyReport extends AmountTotals { date: string }`
  - `export interface MonthlyReport extends AmountTotals { year: number; month: number; days: (AmountTotals & { date: string })[] }` — `days` has exactly `daysInMonth(year, month)` entries, one per calendar day, in order, zero-filled where there's no activity.
  - `export interface AnnualReport extends AmountTotals { year: number; months: (AmountTotals & { month: number })[] }` — `months` always has exactly 12 entries (`month: 1..12`), zero-filled where there's no activity.
  - `export async function getDailyReport(supabase: SupabaseClient, adminSupabase: SupabaseClient, date: string): Promise<DailyReport>`
  - `export async function getMonthlyReport(supabase: SupabaseClient, adminSupabase: SupabaseClient, year: number, month: number): Promise<MonthlyReport>`
  - `export async function getAnnualReport(supabase: SupabaseClient, adminSupabase: SupabaseClient, year: number): Promise<AnnualReport>`

`getAnnualReport`: call both range functions in parallel over `${year}-01-01`..`${year}-12-31`; build `months` by looping `1..12`, summing every date-keyed map entry whose `"YYYY-MM-DD"` falls in that month (compare the 6th–7th characters of the key to the padded month number); totals are the sum across all 12 months.
